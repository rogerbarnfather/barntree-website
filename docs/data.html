Where your data lives

Plain JSON in a folder you commit.

Every Barn tool keeps its files in one .barn/ folder at the project’s root. Barntree’s are in .barn/barntree/. Commit .barn/ with the rest of the project.

$ find .barn -type f | sed … | sort -u
.barn/barntree/template-history/catalogue.barntree.json
.barn/barntree/template-history/save.lock
.barn/barntree/trees/Allotment.barntree.json
.barn/barntree/workspace/construction/<sha256>/<sha256>.barntree.json
.barn/barntree/workspace/construction/<sha256>/current.barntree.json
.barn/barntree/workspace/construction/<sha256>/save.lock
WhereWhat it holds
trees/The Templates, one .barntree.json file each, named after the Template. A subfolder is fine.
template-history/The Templates’ revisions: one catalogue file holding every immutable revision, with the Templates’ identities, and a save.lock.
workspace/construction/One folder per Construction: a file for each revision, current.barntree.json, and a save.lock.

A Template’s identity is its name, not its path. A Template is found by the name inside its file. The folder is made when the first Template is saved.

The Template document #

FieldMeaning
formatVersionThe only version there is is 1. Any other is refused.
name, descriptionThe Template’s name, and what it is for. Neither can be blank.
rootThe identifier of the root type.
tagsOptional. The tags a type may carry, each with its meaning.
typesAt least one, by identifier. Each has a name, a meaning and a kind (leaf, list or map); of is a list’s one type or a map’s types, and left out for a leaf; tags are declared tags, each once.
treeOptional. root is the root item’s id; each entry of items has its type, a name (the root and members only) and containing: an object of type to id for a map, a list of ids for a list, left out for a leaf.

Map entries and references are written in alphabetical order, and Barntree puts them in order whenever it reads, edits or writes a Tree, without changing any id or any list’s sequence.

How it is written #

A save locks the catalogue and compares a SHA-256 token of the exact current file, so a stale draft can’t overwrite an outside edit. The new file is written next to the old one and swapped in atomically. If a save is interrupted, the next operation recovers it. This protects against a partial file; it is not a promise against power loss, a network file system, or an outside writer that ignores the lock.

A broken, unreadable or unnameable file is reported, with its path. See when something goes wrong.
